## 2. Objective and real-world problem

Add prompt caching to the triage tool mode of T-014 and to the chat of T-010. In the tool mode, put one cache breakpoint at the end of the system prompt, so that the tool, the rules and the three examples are one cached prefix. In the chat, use automatic caching for the history. Add the cache prices to the T-001 price table, show the cache write and read tokens in the measurement line, and prove with tests that the prefix is byte-identical for every message. Then run the sample set with and without the cache, and compare the cost and the time to first token.

**Real-world problem.** Teams turn on prompt caching and assume that it works. Then a timestamp, an id or a changed tool order makes every call a cache miss, and the bill goes up, because each miss pays the write price. The API gives no error. Other teams compute the cost from `input_tokens` only and report a saving that is not real. This ticket adds caching with tests that catch a changing prefix, a cost function that counts all input fields, and a measurement that shows the real saving.

## 5. Functional and technical requirements

**Functional**

1. `python -m assistant.triage --mode tool --cache "message text"` sends the T-014 request with one cache breakpoint at the end of the system prompt. Without `--cache`, the tool mode sends the T-014 request with no change. The other modes do not change.
2. The measurement line gets two fields in every mode: `cache_write` (`usage.cache_creation_input_tokens`) and `cache_read` (`usage.cache_read_input_tokens`). They are 0 when the request has no breakpoint. After a retry, they show the sum over all calls of the triage, as the token fields of T-014 do. Example: `mode=tool answer=ok retries=0 valid=yes cache_write=0 cache_read=900`. The input token field of T-001 still shows `usage.input_tokens`. The cost field uses all three input fields.
3. `python scripts/triage_eval.py --modes tool --cache off,on` runs every message of `samples/helpdesk.jsonl` in the tool mode on `claude-haiku-5-5`, first without and then with the cache. It prints one row for each run, with the columns of T-014 and three more: mean cache write tokens, mean cache read tokens and median TTFT. Without `--cache`, the script works as in T-014.
4. `python -m assistant.chat --cache` uses a breakpoint on the system prompt and automatic caching for the history. The measurement line of each turn has the T-010 fields and `cache_write` and `cache_read`. Without `--cache`, the chat sends the T-010 requests with no change.

**Technical**

1. `llm.py` stays the only module that calls the API. Its call function accepts `system` as a string or as a list of text blocks, and gets the optional parameter `cache_control` (the top-level field of automatic caching). Without them, the request is the same as before.
2. A new pure module `assistant/caching.py` holds `MIN_CACHE_TOKENS` (512), `MAX_BREAKPOINTS` (4), `cached_system(text)`, `count_breakpoints(request)`, `prefix_bytes(request)` and `cache_tokens(usage)`. It does not import the SDK, makes no network call and prints nothing.
3. `cached_system(text)` returns one text block with `"cache_control": {"type": "ephemeral"}`. `count_breakpoints` counts the `cache_control` fields in the tools, the system blocks and the message blocks, plus 1 for a top-level `cache_control`. `prefix_bytes` returns `json.dumps([request["tools"], request["system"]]).encode()`, with the request keys of the tool mode. `cache_tokens(usage)` returns the write and read counts, and gives 0 for a field that is missing or `None`.
4. `triage.py` gets a pure function `tool_request(message, cache=False)`. It returns the fields of the tool-mode request: `tools`, `tool_choice`, `system` and `messages`. The tool mode and its retries send these fields. With `cache=False` (the default), the fields are equal to the T-014 request.
5. The tool-mode request has exactly one breakpoint, on the last system block. No message block has `cache_control`: the new message changes on every call.
6. The prefix (the tool and the system prompt) contains no time, no date, no id, no user data and no value built from a `set` or a dictionary with a changing order. The tool comes only from `build_triage_tool()` of T-014, which must give the same bytes on every call and in every process.
7. A retry of `triage_with_tool` adds turns after the breakpoint and keeps the same tool and system prompt, so a retry reads the prefix.
8. In `pricing.py`, add the cache multipliers with a comment that names the date you checked the Pricing page: a write costs 1.25 times the input price (5 minutes) or 2 times (1 hour). A read costs 0.05 times on Opus 5.5 and Sonnet 5.5, and 0.1 times on Haiku 5.5. The cost function gets the optional parameters `cache_write_tokens=0`, `cache_read_tokens=0` and `ttl="5m"`. Without them, the result is the same as in T-001. If your table has the long-prompt prices of Haiku 5.5, the prompt length for that rule includes the cache read and write tokens.
9. `Conversation` gets the optional parameter `cache=False`. With `cache=True`, the chat sends `system=cached_system(SYSTEM_PROMPT)` and `cache_control={"type": "ephemeral"}` on each turn. `count_breakpoints` of each chat request is at most `MAX_BREAKPOINTS`. The history budget of T-010 does not change.
10. The tests make no network call and need no API key. Reuse the fake client of T-001. The fake usage has the three input fields.

## 6. Acceptance criteria

1. Given the Opus 5.5 prices of the T-001 table ($4 input, $20 output), 1,100 input tokens, 4,400 cache write tokens and 150 output tokens, the cost is 0.0294. With 4,400 cache read tokens in place of the write, it is 0.00828. With a 1-hour write, it is 0.0426. These are the numbers of the lesson simulator (tolerance 1e-9).
2. Given the Haiku 5.5 prices ($0.10 input, $0.50 output), 100 input tokens, 900 cache write tokens and 150 output tokens, the cost is 0.0001975. With 900 cache read tokens, it is 0.000094. These are the numbers of the lesson worked example (tolerance 1e-12).
3. Given 1,200 input and 300 output tokens on Opus 5.5 and no cache arguments, the cost is 0.0108, as in T-001.
4. Given two different messages, the two tool-mode requests have equal `prefix_bytes`, and only their messages differ.
5. Given two Python processes with different `PYTHONHASHSEED` values, `prefix_bytes` of the tool-mode request is equal.
6. Given `--mode tool --cache`, `count_breakpoints` of the request is 1, and the breakpoint is on the last system block. Given `--mode tool` without `--cache`, the request is equal to the T-014 request.
7. Given a fake response with an invalid tool input and then a valid one, the second request of `triage_with_tool` has the same `prefix_bytes` as the first.
8. Given a fake usage with `cache_creation_input_tokens` 900 and `cache_read_input_tokens` 0, the measurement line contains `cache_write=900 cache_read=0`. Given a fake usage without the two fields, it contains `cache_write=0 cache_read=0`.
9. Given three chat turns with the fake client and `cache=True`, each request has the top-level `cache_control={"type": "ephemeral"}`, a system block with a breakpoint, and at most 4 breakpoints. The tests of T-010 pass without a change.
10. With a real key, two tool-mode calls with different messages, less than 5 minutes apart, on `claude-haiku-5-5`: call 1 has `cache_write` above 0, and call 2 has `cache_read` equal to that number. The handoff records the two measurement lines. If both fields are 0 on both calls, the handoff gives the prefix length from `count_input_tokens` and says that it is below the minimum.
11. With a real key, `scripts/triage_eval.py --modes tool --cache off,on` runs one time. The handoff records the two rows.
12. `pytest` passes with the network off. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the eval run. Each run of the eval sends its first call alone, so that the later calls can read the cache. The script prints its total cost from all three input fields. The unit tests make no paid calls.
- **Reliability:** a cache miss is not an error, and the code must never fail because of it. The answer is the same with and without the cache, so the accuracy of the two eval rows must be equal within the normal variation of the model.
- **Latency:** record the median TTFT of both eval rows. The docs say that you generally see a better TTFT for long documents. The triage prefix is short, so the gain can be small. Report what you measured.
- **Security:** the key comes only from the environment. The prefix holds no user data: employee data goes only into the user turn, after the breakpoint. Caches are isolated for each workspace on the Claude API.
