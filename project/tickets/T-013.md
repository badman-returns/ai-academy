## 2. Objective and real-world problem

Make the result of the helpdesk triage a validated `TriageResult` object. The triage prompt asks for JSON that matches the schema of the model. The code validates every reply, sends the errors back to the model for at most two retries, and then raises a clear error. The measurement line records the number of retries. The new `json` mode of the triage CLI uses them, and the earlier modes do not change. Put the model and the loop in a new module, `assistant/structured.py`, and prove them with tests that are named after the properties they check.

**Real-world problem.** A triage that prints text is enough for a person. A queue, a notice and a dashboard need fields that are always there and always have the correct type. Teams that parse model output without validation get crashes on a small part of the traffic, or silent bad records. This ticket gives the triage a contract, a bounded repair loop and a number that shows when the contract starts to fail.

## 5. Functional and technical requirements

**Functional**

1. `python -m assistant.triage --mode json "message text"` prints the four fields of the validated result, one on each line: `category: ...`, `priority: ...`, `summary: ...` and `needs_human: ...`. The first two lines are the same as in the `labels` mode.
2. In the json mode, `--print-json` prints the validated result as one JSON line instead, from `model_dump_json()`.
3. In the json mode, the measurement line has the fields `mode=json` (T-012) and `answer` (T-009), and two new fields: `retries` (0 to the limit) and `valid` (`yes` or `no`). The token and cost fields show the sum over all calls of the triage. Example: `mode=json answer=ok retries=1 valid=yes`.
4. When the triage fails, the CLI prints one line that names the reason (the status of `check_answer`, or the number of errors after the last retry), prints the measurement line, and exits with a code that is not 0. It prints no stack trace.
5. `--max-retries N` sets the retry limit of the json mode. The default is 2. Allowed values: 0 to 3. Another value gives an error before any API call.
6. `python scripts/triage_eval.py --modes json` runs every message of `samples/helpdesk.jsonl` in the json mode, with the 3 examples of T-011. Its row has the columns of T-012 and two more: the number of replies that were valid at once, and the total number of retries. A failed triage counts as a wrong answer, as a reply of `None` does in T-011.

**Technical**

1. `llm.py` stays the only module that calls the API.
2. `assistant/structured.py` contains `TriageResult`, `TriageError`, `retry_message` and `triage_with_retry`. It does not import the SDK, makes no network call and prints nothing.
3. `TriageResult` uses `ConfigDict(extra="forbid", strict=True)`. Fields: `category` (`Literal["IT", "HR", "facilities", "finance", "other"]`), `priority` (`Literal["low", "medium", "high"]`), `summary` (string, 1 to 200 characters) and `needs_human` (boolean). The two `Literal` types have the values of `CATEGORIES` and `PRIORITIES` of T-011, in the same case. Then `Label(result.category, result.priority)` compares directly with the labels of the sample set.
4. The system prompt of the json mode is `RULES` of T-012, then one line that asks for only one JSON object that matches the schema, then `json.dumps(TriageResult.model_json_schema())`. It does not contain `LABEL_FORMAT`, and it does not repeat the allowed values in a hand-written list. The prompts of the other modes do not change.
5. `build_request` of T-011 gets an optional parameter `json_examples: bool = False`. When it is true, each example assistant turn is the `model_dump_json()` text of a `TriageResult` for that example. Add the keys `summary` and `needs_human` to each line of `samples/triage_examples.jsonl`. Without the parameter, the request is the same as before.
6. `triage_with_retry(send, messages, max_retries=2)` takes a function `send` that calls the model through `llm.py`. It returns the result and the list of responses of all calls. It makes at most `max_retries + 1` calls.
7. For each response, it calls `check_answer` of T-009 first. When the status is not `ok`, it raises `TriageError` at once with the status, with no retry. It validates the `text` of the `check_answer` result, so it never reads a block by its position.
8. On a `ValidationError`, it adds the response content unchanged as an assistant turn, then `retry_message(error)` as a user turn. It does not change the list that the caller passed in.
9. The request never ends with an assistant turn. Do not prefill `{`: the current models return error 400 for a prefill. Do not send `temperature`, `top_p` or `top_k`.
10. The SDK retries of T-001 (`max_retries` on the client) stay as they are. The two limits have different names in the code.
11. The tests make no network call and need no API key. Reuse the fake client of T-001.

## 6. Acceptance criteria

1. Given each reply in `tests/fixtures/triage_replies.json`, `TriageResult.model_validate_json` gives the result in its `expect` field: `valid`, or a `ValidationError` whose first error has that `type`.
2. The `Literal` values of `category` and `priority` are equal to `CATEGORIES` and `PRIORITIES` of T-011, in the same order and case.
3. Given the fake replies [missing field, valid], `triage_with_retry` returns the result after 2 calls. The second request has 3 messages: the first user turn, the first reply content unchanged, and a user turn that contains `needs_human` and "Field required".
4. Given the fake replies [wrong type, wrong type, wrong type] and `max_retries=2`, it raises `TriageError` after exactly 3 calls. The error text says "after 2 retries".
5. Given a fake reply with `stop_reason="max_tokens"` and a cut-off text, `check_answer` gives `incomplete`, and `triage_with_retry` raises `TriageError` after exactly 1 call. The error text names the status.
6. Given `max_retries=0` and an invalid reply, it raises after exactly 1 call.
7. Given usage of 800 input and 50 output tokens for call 1, and 910 and 50 for call 2, at the Haiku 5.5 prices of the T-001 table ($0.10 and $0.50 per million), the measurement line shows `retries=1 valid=yes` and the cost 0.000221 (tolerance 1e-9).
8. The system prompt of the json mode contains `RULES` and the JSON text of `TriageResult.model_json_schema()`, and does not contain `LABEL_FORMAT`. With `json_examples=True`, each example assistant turn validates as a `TriageResult`.
9. With a real key, `scripts/triage_eval.py --modes json` runs once on `claude-haiku-5-5`. The handoff records the row, with the valid-at-once count and the total retries.
10. `pytest` passes with the network off. The tests of T-001, T-009, T-010, T-011 and T-012 pass without a change. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the eval run. The retry limit caps the calls for each message at 3. The script prints its total cost. The unit tests make no paid calls.
- **Reliability:** the triage never returns a half-valid result. Every failure is a `TriageError` with a reason, and every retry is visible in the measurement line.
- **Latency:** each retry adds a full call. Record the total time over all calls, and report the time of the messages that needed a retry separately in the handoff.
- **Security:** the key comes only from the environment. The replies contain text from employee messages, so the CLI does not write full replies to a log. The retry message contains only field names and error messages, not the input values.
