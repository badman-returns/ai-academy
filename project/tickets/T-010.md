## 2. Objective and real-world problem

Add `python -m assistant.chat`, an interactive chat on top of the T-001 client. A new module, `assistant/chat.py`, holds a `Conversation` class that owns the history: the system prompt in the top-level `system` field, and the list of user and assistant messages. Each turn sends the full history through `llm.py`. The measurement line shows the turn number and the number of messages sent, so you can see the history grow. When the history gets too large, the conversation removes the oldest pairs with `trim_history` from T-007.

**Real-world problem.** Chat features often fail in three ways. The assistant forgets what the user said two turns before, because the code sent only the new question. A failed call leaves a question with no answer, and the next request has two user messages in a row. Or the history grows until each request is too expensive or too large for the context window. This ticket gives the assistant a history that is correct, safe after a failure and limited in size, and tests that prove it.

## 5. Functional and technical requirements

**Functional**

1. `python -m assistant.chat` starts a chat. It reads one line from the user, sends the turn, streams the answer and prints the measurement line. Then it waits for the next line. An empty line or `/quit` ends the chat. `/reset` removes the history and keeps the system prompt.
2. The chat accepts the T-001 options `--model`, `--max-tokens` and `--system`, and the T-002 option `--max-input-tokens` (default from `ASSISTANT_MAX_INPUT_TOKENS`). The input limit is the history budget.
3. The measurement line of T-001 gets three new fields: `turn` (1, 2, 3 ...), `messages` (the number of messages sent) and `trimmed` (the number of messages removed before this turn). Example: `turn=4 messages=7 trimmed=0`.
4. When a call fails, the chat prints the T-001 error message, and the history stays as it was before the turn. The user can type the question again.
5. When the answer check of T-009 does not give the status `ok` (for example `no_answer`), the chat prints the status, does not store the turn, and the history stays as it was before the turn.

**Technical**

1. `llm.py` stays the only module that calls the API. Its call function gets an optional parameter `messages: list[dict] | None = None`. Without it, the request is the same as in T-001.
2. `assistant/chat.py` contains `Conversation(system, model, max_tokens, max_input_tokens=None)` with the methods `send(client, text)` and `reset()`, a read-only property `messages`, and a pure function `check_turn_order(messages)`.
3. `check_turn_order` raises `ValueError` when the list is empty, does not start with `user`, has two messages with the same role in a row, has a message with the role `system`, or ends with `assistant`. `send` calls it on each request before the API call.
4. The system prompt goes only into the top-level `system` argument. The messages list never contains the system prompt.
5. `send` builds the request as a new list (history plus the new user message). It replaces the stored history only after a successful call, with the request and the assistant message together.
6. The stored assistant message contains `response.content` unchanged, with all its blocks (thinking blocks too). The answer text comes from `check_answer` of T-009, never from `content[0]`.
7. History budget: when `max_input_tokens` is set, each stored message keeps a token count. For a user message, count it one time with `count_input_tokens` of T-002. For an assistant message, use `usage.output_tokens` of its response. Before the call, convert the history to T-007 `Message` objects and call `trim_history(messages, system_tokens, max_tokens, context_window=max_input_tokens + max_tokens)`. Then count the trimmed request with `count_input_tokens`. The exact count decides: if it is still above the limit, remove one more pair and count again. If only the new question is left and it does not fit, print the T-002 limit message and make no call.
8. The tests make no network call and need no API key. Reuse the fake client of T-001. It records the arguments of each call.

## 6. Acceptance criteria

1. Given four turns with the fake client, the four recorded calls have 1, 3, 5 and 7 messages, and each call starts with all messages of the call before it, in the same order.
2. In every recorded call, the `system` argument is the system prompt, and no message in the list has the role `system`.
3. `check_turn_order` accepts [user], and [user, assistant, user]. It raises `ValueError` for [], [assistant, user], [user, user], [user, assistant] and [system, user].
4. Given a fake client that raises a timeout on turn 3, the history after the failed turn has the same 4 messages as before it, and the next successful turn sends 5 messages.
5. Given a fake response with a thinking block and a text block, the stored assistant content has both blocks unchanged, and the next recorded call sends them back.
6. Given a system prompt of 1,000 tokens, 10 earlier pairs of 200 and 300 tokens, a new question of 200 tokens, `max_tokens` 1,024 and `max_input_tokens` 4,976, the request keeps the newest 7 pairs and the new question (15 messages, 4,700 input tokens), and the measurement line shows `trimmed=6`. These are the numbers of T-007 criterion 7.
7. Given a fake response with status `no_answer`, the history does not change, and the chat prints the status.
8. With a real key, a chat of the four questions of the lesson on `claude-haiku-5-5` prints four measurement lines with growing input tokens, and the answer to turn 4 names the order number NW-4471. The handoff records the four lines.
9. `pytest` passes with the network off. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests. Each turn sends the full history, so the input cost of a chat grows with the square of the number of turns (lesson 1.7). The measurement line shows the cost of each turn. The unit tests make no paid calls.
- **Reliability:** the stored history always passes `check_turn_order`, also after a failure, a timeout or a turn with no answer. A request that cannot fit is stopped before the call.
- **Latency:** the time to the first token grows with the input. Record the TTFT of each turn in milestone 4 and compare turn 1 with turn 4.
- **Security:** the key comes only from the environment. The history contains user data, so the chat never writes it to a log file. Only `--save` (stretch) writes it, to a file that the user names.
