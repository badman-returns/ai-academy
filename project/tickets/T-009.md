## 2. Objective and real-world problem

Add effort control to the T-001 client and CLI. Make the answer check safe for responses that contain thinking blocks or that stop at `max_tokens`. Put the logic in a new pure module, `assistant/thinking.py`, and prove it with tests that are named after the properties they check. Then write a small effort sweep that measures the cost per correct answer of two effort levels on your own eval set.

**Real-world problem.** Teams turn on a higher effort to fix a few hard requests. Then the bill goes up on every request, some requests return no answer because the thinking used all of `max_tokens`, and code that reads the first block crashes. This ticket gives the assistant the controls and the checks to prevent these failures, and a measurement to choose the effort with data.

## 5. Functional and technical requirements

**Functional**

1. `ask --effort high "question"` sends the effort to the model. The allowed values are `low`, `medium`, `high`, `xhigh` and `max`. Without `--effort`, the request is the same as in T-001.
2. `ask --show-thinking "question"` asks for a thinking summary and prints it under the header "Thinking summary", before the answer. Without this option, the CLI prints no thinking text.
3. The measurement line of T-001 gets two new fields: `effort` (the effort level, or `default`) and `answer` (`ok`, `incomplete`, `no_answer` or `refusal`). Example: `effort=high answer=ok`.
4. When the response has no text block and `stop_reason` is `max_tokens`, the CLI prints one clear line that names max_tokens and the output tokens used, suggests a larger `--max-tokens` or a lower `--effort`, and exits with a code that is not 0.
5. `python scripts/effort_sweep.py` runs every question of `data/reasoning_eval.json` at two effort levels (default: `low` and `high`) on `claude-haiku-5-5`, and prints one table row for each question kind and effort: correct answers, mean output tokens, median total time, total cost and cost per correct answer.

**Technical**

1. `llm.py` stays the only module that calls the API. Its call function gets two optional parameters: `effort: str | None = None` and `show_thinking: bool = False`.
2. With an effort, the request contains `output_config={"effort": effort}`. With `show_thinking`, it contains `thinking={"type": "adaptive", "display": "summarized"}`. Never send `budget_tokens`, `{"type": "disabled"}` or `temperature`.
3. `assistant/thinking.py` contains pure functions only: `EFFORT_LEVELS`, `validate_effort`, `check_answer`, `cost_per_correct` and `choose_effort`. No API calls, no printing, no global state.
4. `validate_effort` raises `ValueError` with a message that lists the five allowed values. The CLI calls it before any API call.
5. `check_answer(stop_reason, blocks)` returns a dataclass with `status`, `text` (joined from the blocks with type "text" only) and `thinking_summary`. It never reads a block by its position.
6. The cost comes from `usage.input_tokens` and `usage.output_tokens` with the T-001 price table. Do not count the tokens of the answer text yourself.
7. The streamed answer shows text only. Thinking deltas never appear in the answer.
8. The tests make no network call and need no API key. Reuse the fake client of T-001.

## 6. Acceptance criteria

1. Given `effort="high"`, when the call function runs with the fake client, then the request arguments contain `output_config={"effort": "high"}` and contain no `budget_tokens`.
2. Given no effort and `show_thinking=False`, the request arguments are equal to the T-001 request, and all T-001 tests pass without a change.
3. Given `--effort extreme`, the CLI prints an error that lists the five allowed values, exits with a code that is not 0, and the fake client records 0 calls.
4. Given the content [thinking block, text block "100"] and `stop_reason="end_turn"`, `check_answer` returns status `ok` and text "100". The thinking text is not in `text`.
5. Given the content [thinking block only] and `stop_reason="max_tokens"`, `check_answer` returns status `no_answer`, and the CLI prints the max_tokens line with no stack trace.
6. Given usage of 900 input and 3,050 output tokens at the Opus 5.5 prices of the T-001 table ($4 and $20 per million), the cost is 0.0646 (tolerance 1e-9). This is the effort-high example of the lesson.
7. Given 100 runs that cost $1.56 in total with 62 correct answers, `cost_per_correct` returns 0.02516 (tolerance 1e-5). Given 0 correct answers, it returns `None`.
8. With a real key, `ask --model claude-haiku-5-5 --effort low` and `--effort high` on the refund question of the eval set both print a measurement line. The handoff records both lines.
9. `pytest` passes with the network off. The key value appears in no file and in no log line.

Format of `data/reasoning_eval.json`, with two example questions. The script adds an instruction to end the answer with a line that starts with "ANSWER:" and the value, for example "ANSWER: 100". It grades the value by an exact match.

```
[
  {"id": "classify-1", "kind": "classify",
   "question": "Labels: billing, shipping, account, product, refund, other. Ticket: 'I was charged twice for order 5521.' Reply with one label.",
   "expected": "billing"},
  {"id": "refund-1", "kind": "multi_step",
   "question": "Rules: (1) An item returned within 30 days gets a full refund. (2) An item returned after 30 days and within 60 days gets 50%. (3) Shipping is refunded only if an item was damaged. (4) Subtract the coupon share of each item, in proportion to its price, before you apply rule 1 or 2. Order: item A $80, returned on day 20, damaged. Item B $40, returned on day 45, not damaged. Shipping $10. Coupon $12 on the order. What is the refund in USD? Give a number.",
   "expected": "100"}
]
```

Check the example: the coupon shares are $8 for A and $4 for B. A: $80 − $8 = $72, full refund. B: ($40 − $4) × 50% = $18. Shipping: A was damaged, so $10. Total: $72 + $18 + $10 = $100.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the sweep. The sweep prints its total cost. Run it one time, then read the results. The unit tests make no paid calls.
- **Reliability:** never show an incomplete or empty response as a complete answer. Every `max_tokens` stop is visible in the measurement line.
- **Latency:** record the total time of each call in the sweep. A higher effort gives a longer time before the first answer word. Report the median, and say that 10 questions are too few for a p95.
- **Security:** the key comes only from the environment. The thinking summary can contain user data from the prompt, so the CLI prints it only with `--show-thinking` and never writes it to a log.
