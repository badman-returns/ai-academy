## 2. Objective and real-world problem

Give the prompts of the assistant a version and tests. Move the triage rules and the default chat system prompt into text files with a version name. Add a content hash to the measurement line. Add offline prompt tests that make no API call. Then add a regression gate: a script that runs the triage on the labeled sample set, compares the run with a saved baseline, and passes or fails the prompt change with clear reasons.

**Real-world problem.** Teams change prompts as text in code or in a database, with no version and no test. When answers get worse, nobody can say which prompt made them, and the regression is found by users. This ticket makes every prompt change visible in a diff, traceable in each measurement line, and checked against a baseline before it ships.

## 5. Functional and technical requirements

**Functional**

1. The triage CLI works as before in every mode. The measurement line gets two fields: `prompt` (the version, for example `triage-v3`) and `prompt_hash` (12 lowercase hexadecimal characters). They come after the fields of T-015. Example: `mode=json answer=ok retries=1 valid=yes cache_write=0 cache_read=0 prompt=triage-v3 prompt_hash=<12 hex>`.
2. `python -m assistant.chat` shows `prompt=chat-v1` and its `prompt_hash` on the measurement line. With `--system`, it shows `prompt=custom`.
3. `python scripts/prompt_gate.py --mode json` first runs the offline prompt tests with pytest. When they fail, it prints the failed tests, makes no API call and exits with code 1.
4. Then it compares the request hash of the current prompt with `samples/triage_baseline.json`. When the hashes are equal, it prints `no prompt change`, makes no API call and exits with code 0.
5. Otherwise it runs every message of `samples/helpdesk.jsonl` in the given mode on `claude-haiku-5-5`, with the code of `scripts/triage_eval.py`. It prints the baseline line, the candidate line, the fixed and broken case ids, the cost of the run and `verdict: PASS` or `verdict: FAIL` with one line for each reason. The exit code is 0 for a pass and 1 for a fail.
6. `--update-baseline` writes the run to `samples/triage_baseline.json` only after a pass. After a fail, it writes nothing and says so.

**Technical**

1. Move the text of `RULES` into `assistant/prompts/triage_rules.txt`, and the fixed chat system prompt of T-010 into `assistant/prompts/chat_system.txt`. The first line of each file is `version: <name>-v<n>`, then one empty line, then the text. Start with `triage-v3` and `chat-v1`.
2. `LABEL_FORMAT` stays in `triage.py`, and `ANSWER_INSTRUCTION` and `REASON_INSTRUCTION` stay in `reasoning.py`, next to the code that parses their format.
3. A new pure module `assistant/prompts.py` holds `Prompt` (name, version, text), `load_prompt`, `all_prompts`, `short_hash` (SHA-256, first 12 hexadecimal characters), `source_hash(name)` and `request_hash(system, tools, examples)`. It makes no API call and prints nothing. Never use the Python function `hash()`.
4. `source_hash("triage")` covers the body of `triage_rules.txt` and the bytes of `samples/triage_examples.jsonl`. `source_hash("chat")` covers the body of `chat_system.txt`. `assistant/prompts/prompts.lock.json` maps each version to its source hash.
5. `request_hash` covers the fixed part of the request: the rendered system prompt of the mode, the tools (tool mode) and the example turns. It does not cover the new message. `triage.py` gets `TRIAGE_MODES` (`labels`, `direct`, `reason`, `json` and `tool`), `fixed_request(mode)` and `request_fingerprint(mode)`. `fixed_request` returns the system prompt, the tools and the example turns of the mode: it calls `build_request` with the flags of the mode (`answer_tags`, `json_examples`). For the tool mode, `fixed_request` uses the `tools` and `system` fields of `tool_request(message, cache=False)` of T-015, so the request hash is the same with and without `--cache`: the cache changes the cost, not the prompt. `request_fingerprint` returns the `request_hash` of that fixed part.
6. `triage.py` and `chat.py` read the prompt files one time, when the module loads. Reading a file gives the same bytes in every process, so the T-015 tests of the byte-identical prefix pass without a change.
7. A new pure module `assistant/gate.py` holds `GateResult` (passed, reasons, fixed, broken) and `compare(baseline, run)`. It fails when the mode or the model differs, when correct answers are fewer than the baseline, when invalid first replies are more than the baseline, or when a must-pass case is not correct.
8. The baseline file has the keys `mode`, `prompt`, `prompt_hash`, `model`, `correct`, `total`, `invalid_first`, `must_pass` and `cases`. Each case has `id`, `expected`, `got`, `valid_first`, `retries` and `correct`. A failed triage has `got` `null` and counts as wrong.
9. `must_pass` holds at least two ids of `samples/helpdesk.jsonl`: the message that tries to change the rules (T-011), and one message with priority high.
10. No prompt text contains a date, a time, a user name or a key. No code adds such a value to the fixed part of a request.
11. The tests make no network call and need no API key. Reuse the fake client of T-001.

## 6. Acceptance criteria

1. After milestones 1 to 3, every mode sends the same system prompt as before (compare with a string saved before the move), and `prefix_bytes(tool_request("test", cache=True))` of T-015 is equal to its value before the move. The tests of T-001 and T-010 to T-015 pass without a change.
2. Given `triage_rules.txt` with the version line `version: triage-v3`, `load_prompt` returns the version `triage-v3` and the body without the version line. A file without the version line, or with the version `v3`, raises `ValueError`.
3. Given any mode, `request_fingerprint(mode)` returns 12 lowercase hexadecimal characters, and two calls return the same value. Two modes with a different system prompt return different values.
4. Given a change of one character in the rules body and no new version, `test_changed_text_has_a_new_version` fails with a message that names the version. With the new version in the file and in the lock file, it passes.
5. Given a system prompt with `Today is 2026-11-02.` in any mode, `test_prompt_has_no_date_or_time` fails.
6. Given a baseline with 16 of 20 correct, 1 invalid first reply and `must_pass` m01 and m20, and a run with 18 of 20 correct, 1 invalid first reply, m07 and m12 fixed and nothing broken, `compare` returns `passed=True`, `fixed=["m07", "m12"]` and `broken=[]`.
7. Given the same baseline and a run with 17 of 20 correct that fixes m04 and m15 and breaks m20, `compare` returns `passed=False` with one reason that names m20.
8. Given the same baseline and a run with 15 of 20 correct and 9 invalid first replies, `compare` returns `passed=False` with two reasons: the correct answers and the invalid first replies.
9. Given a run with a different model, `compare` returns `passed=False` with a reason that names the model, also when every case is correct.
10. Given the current prompt and a baseline with the same `prompt_hash`, `prompt_gate.py` prints `no prompt change`, makes 0 calls to the fake client and exits with code 0. Given a failed offline test, it makes 0 calls and exits with code 1.
11. Given `--update-baseline` and a failed gate, the baseline file does not change.
12. With a real key, milestone 4 records one real prompt change: the diff, the offline test result, the two gate lines, the fixed and broken lists, the verdict and the decision.
13. `pytest` passes with the network off. The key value appears in no file and in no log line.

## 7. Milestones

1. **Save the current prompts (guided).** Before you move anything, write a test that saves the system prompt of each mode and of the chat as a string in `tests/fixtures/system_prompts_before.json`. Save also the hex text of `prefix_bytes(tool_request("test", cache=True))` of T-015 in the same file. Then move the text into the two prompt files, write `prompts.py`, and check that the test still passes. This proves acceptance criterion 1.
2. **The hash and the offline tests (guided).** Write `source_hash`, `request_hash`, `request_fingerprint` and the lock file. Write `tests/test_prompts.py` for criteria 2 to 5. Add `prompt` and `prompt_hash` to the measurement lines of the triage and the chat.
3. **The gate (independent).** Write the tests for criteria 6 to 11 with small fake runs. Then write `gate.py` and `scripts/prompt_gate.py`. Reuse the per-message code of `triage_eval.py`. Do not copy it.
4. **One real prompt change (independent).** Run `prompt_gate.py --mode json --update-baseline` one time on the unchanged prompt to save the first baseline. Then make one small change to the rules that you think helps (for example, a rule for a confusion that you saw in T-011). Change the version, update the lock file, and run the gate. Record the result and your decision in `handoffs/T-016-handoff.md`. Ship the change only if the gate passes.

Cost of milestone 4: about 3 gate runs × 20 messages = 60 calls, and at most 180 calls if every message needs two retries. If each call uses 1,000 input and 150 output tokens, the cost at the Haiku 5.5 prices of the T-001 table is 60 × (1,000 × $0.10 + 150 × $0.50) / 1,000,000 = about $0.0105, and about $0.0315 for 180 calls. The script prints the real total.

Stretch, optional: run the gate of your change two times on the same prompt. Which cases flip between the two runs? Remove an unstable case from `must_pass`.

## 10. Security, reliability, performance and cost

- **Cost:** the offline tests and the hash check run before any paid call. Use `claude-haiku-5-5` for every gate run. The script prints its total cost.
- **Reproducibility:** the baseline names the mode, the prompt version, the request hash and the model. Any person can find the exact prompt of a baseline in git.
- **Traceability:** every measurement line of the triage and the chat names the prompt version and hash.
- **Security:** the key comes only from the environment. No prompt file, lock file or baseline contains a key or personal data.
