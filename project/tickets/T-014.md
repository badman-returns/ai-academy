## 2. Objective and real-world problem

Make the API enforce the triage schema. Add a fifth mode, `tool`, to the triage CLI. Build the tool definition from the `TriageResult` model of T-013 with one function, send it with `"strict": true`, find the tool call by block type and validate its input with the same model. Then run the labeled sample set in the `json` mode of T-013 and in the `tool` mode, and compare the valid replies, the retries, the accuracy and the cost.

**Real-world problem.** Teams that parse JSON from a prompt spend tokens and time on retries, and they keep two descriptions of the result that drift apart. Teams that turn on enforcement often delete their validation and then miss refusals, missing tool calls and wrong values. This ticket gives the assistant enforcement with one source for the schema, keeps the validation, and measures what changed.

## 5. Functional and technical requirements

**Functional**

1. `python -m assistant.triage --mode tool "message text"` uses strict tool use. It prints the four fields of the validated result, one on each line, as the `json` mode does. `--print-json` and `--max-retries N` work as in T-013.
2. In the tool mode, the measurement line has the fields of T-013 with `mode=tool`. The token and cost fields show the sum over all calls of the triage. Example: `mode=tool answer=ok retries=0 valid=yes`.
3. When a reply has no `record_triage` tool call, or the tool input fails validation, the code counts the reply as invalid and retries with the limit of T-013 (default 2).
4. When `stop_reason` is `refusal` or `max_tokens`, the code does not retry. The CLI prints one line that names the status (`refusal` or `incomplete`, the names of T-009), prints the measurement line, and exits with a code that is not 0. It prints no stack trace.
5. `python scripts/triage_eval.py --modes json,tool` runs every message of `samples/helpdesk.jsonl` in both modes on `claude-haiku-5-5`. The tool row has the same columns as the json row of T-013. In the tool mode, "valid at once" counts the first replies with a valid tool call. A failed triage counts as a wrong answer.

**Technical**

1. A new pure module `assistant/schema_tool.py` holds `TOOL_NAME`, `TOOL_DESCRIPTION`, `close_objects`, `build_schema`, `build_tool`, `build_triage_tool`, `find_tool_use`, `tool_retry_turn` and `triage_with_tool`. It does not import the SDK, makes no network call and prints nothing.
2. The tool definition comes only from `build_triage_tool()`. No file contains a hand-written copy of the schema.
3. `build_schema` starts from a copy of `TriageResult.model_json_schema()` and sets `"additionalProperties": false` on the root object and on each object in `$defs`. The tool has `"strict": true` at the top level.
4. The request uses `tool_choice={"type": "auto"}`. Never send `{"type": "any"}` or `{"type": "tool"}`: the default model `claude-opus-5-5` rejects them with error 400.
5. The system prompt of the tool mode is `RULES` of T-012, then one line that tells the model to call `record_triage`, then the 3 examples of T-011 in `<example>` tags inside `<examples>` tags. Each example has the message in `<message>` tags and the `model_dump_json()` text of its `TriageResult`. The prompt does not contain `LABEL_FORMAT` or the schema text: the tool carries the schema. The messages list has one user turn, the new message in `<message>` tags. An example assistant turn with text would teach a text reply.
6. `find_tool_use(blocks, name)` returns the first `tool_use` block with that name, or `None`. It never reads a block by its position.
7. `triage_with_tool(send, messages, max_retries=2)` has the contract of `triage_with_retry` of T-013: it returns the result and the list of responses, makes at most `max_retries + 1` calls, and does not change the list that the caller passed in.
8. For each response, it checks `stop_reason` first. `refusal` and `max_tokens` raise `TriageError` at once with the status `refusal` or `incomplete`. Do not use `check_answer` here: it reads only the text blocks, and the result is in a `tool_use` block.
9. It validates the tool input with `TriageResult.model_validate`, the same model as the json mode. For a retry, it adds the response content unchanged as an assistant turn, then the user turn from `tool_retry_turn(block, error)`.
10. `tool_retry_turn` gives one of two user turns. After a tool call that fails validation, the first block is `{"type": "tool_result", "tool_use_id": block.id, "is_error": true, "content": retry_message(error)}`: a user turn with text only after a `tool_use` block gives error 400. After a reply with no tool call, the turn is the text "Call the record_triage tool with your result."
11. The call function of `llm.py` gets the optional parameters `tools` and `tool_choice`. Without them, the request is the same as before. `llm.py` stays the only module that calls the API. The cost comes from `usage.input_tokens` and `usage.output_tokens` with the T-001 price table.
12. The tests make no network call and need no API key. Reuse the fake client of T-001.

## 6. Acceptance criteria

1. Given `build_triage_tool()`, the result has the keys `name`, `description`, `input_schema` and `strict`; `strict` is `True`; the name matches `^[a-zA-Z0-9_-]{1,128}$`; and every object in the schema (the root and each object in `$defs`) has `additionalProperties` `false`.
2. Given the schema of the tool, its `required` list has the four fields of `TriageResult`, and the enum values of `category` and `priority` are equal to `CATEGORIES` and `PRIORITIES` of T-011, in the same order and case.
3. Given a fake response with the content [text block, `tool_use` block with a valid input], `triage_with_tool` returns the result after 1 call. With the CLI, the measurement line shows `mode=tool answer=ok retries=0 valid=yes`.
4. Given the fake replies [text block only, valid tool call], it returns the result after 2 calls. The second request has 3 messages: the first user turn, the first reply content unchanged, and a user turn with text that names `record_triage`.
5. Given the fake replies [tool call with the input of the `type` reply of `tests/fixtures/triage_replies.json`, valid tool call], it returns the result after 2 calls. The third message of the second request is a user turn whose first block is a `tool_result` with the same `tool_use_id`, `is_error` true, and content that contains `needs_human`.
6. Given three invalid tool calls and `max_retries=2`, it raises `TriageError` after exactly 3 calls. The error text says "after 2 retries".
7. Given a fake response with `stop_reason="refusal"`, it raises `TriageError` after exactly 1 call, and the CLI prints the refusal line with no stack trace. With `"max_tokens"`, the status is `incomplete`, also after 1 call.
8. Given `--mode tool`, the request has `tool_choice={"type": "auto"}`, one tool with `"strict": true`, a system prompt that contains `RULES` and `record_triage` and does not contain `LABEL_FORMAT`, and one user turn. The other modes send the same requests as before, and the tests of T-001 and T-009 to T-013 pass without a change.
9. Given 986 input and 90 output tokens at the Opus 5.5 prices of the T-001 table ($4 and $20 per million), the cost is 0.005744 (tolerance 1e-9). This is the enforced request of the lesson example.
10. With a real key, `scripts/triage_eval.py --modes json,tool` runs one time on `claude-haiku-5-5`. The handoff records the two rows.
11. `pytest` passes with the network off. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the eval run. The retry limit caps the calls for each message at 3. The script prints its total cost. The unit tests make no paid calls.
- **Reliability:** never show a refusal, a `max_tokens` stop or a missing tool call as a triage result. Every such case is visible in the measurement line or the eval row.
- **Latency:** the first request with a new schema is slower, because the API compiles the grammar. Record the time of the first call and of a later call in the handoff.
- **Security:** the key comes only from the environment. The API caches the schema for up to 24 hours, so put no personal data in property names, enum values or the tool description.
