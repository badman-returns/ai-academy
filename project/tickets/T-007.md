## 2. Objective and real-world problem

Add a KV cache to your transformer block from T-005, in `assistant/kv_cache.py`, and prove with tests that the cached decode gives the same outputs as the full pass. Add a function that computes the cache size of a model. Then write `assistant/context_budget.py`: a check that a request fits in the context window, and a function that trims the oldest chat turns until it fits.

**Real-world problem.** Chat features often get slower and more expensive with each turn, and then fail with an error when the history is too long. Teams also choose a context length or a model without an estimate of the memory that it needs. A cache that you wrote and tested, a size formula, and a budget check before each call give you the tools to explain and prevent these problems.

## 5. Functional and technical requirements

**Functional**

1. `KVCache` is a dataclass with `keys: list[list[float]]` and `values: list[list[float]]`. `len(cache)` returns the number of cached tokens. It holds one block and one head, as in T-005.
2. `decode_step(x, params, cache) -> list[float]` runs the pre-LN block of T-005 for one new token vector `x`: layer norm 1, then q, k and v. It adds k and v to the cache, then attends with q over all cached keys and values, then multiplies by `w_o` and adds the residual. Then it runs layer norm 2, the feed-forward layer and the second residual. It returns the output vector.
3. `run_with_cache(xs, params) -> tuple[list[list[float]], KVCache]` creates a new cache, calls `decode_step` for each token in order, and returns the outputs and the cache.
4. `kv_cache_bytes(n_tokens, n_blocks, n_kv_heads, d_head, bytes_per_value=2) -> int` returns 2 × n_blocks × n_kv_heads × d_head × bytes_per_value × n_tokens.
5. In `assistant/context_budget.py`: `fits_context(input_tokens, max_tokens, context_window) -> bool`; `history_input_tokens(system_tokens, turns) -> list[int]`, which returns the input tokens of each request in a chat; and `trim_history(messages, system_tokens, max_tokens, context_window) -> list[Message]`.
6. `python -m assistant.kv_cache` loads `data/block_toy.json`, prints the cached output and the full-pass output of each token at 3 decimals and the largest difference, prints the cache length after each step, and prints the cache size for the lesson shape (32 blocks, 32 and 8 KV heads, head size 128, 2 bytes) at 4,096 and 100,000 tokens.

**Technical**

1. Import `layer_norm`, `feed_forward` and `BlockParams` from T-005, and the attention function from T-004. Do not copy them. For the attention of one new token, call the T-004 function with one query row and the cached keys and values, with the causal mask off: the cache holds only earlier tokens and the token itself.
2. `decode_step` changes only the cache that it receives. It does not change `x` or `params`. No global state, and no default argument that holds a cache.
3. `Message` is a dataclass with `role` (`"user"` or `"assistant"`) and `tokens` (an int). The caller gets the counts from the token counting endpoint of T-001. The budget functions make no API call.
4. `trim_history` removes the oldest messages in whole pairs (one user message and the answer after it), so the history still starts with a user message. It never removes the last message (the new question). It keeps the order. When the request does not fit even with no history, it raises `ContextBudgetError` with a message that gives the input tokens, max_tokens and the window.
5. `fits_context` returns True when input_tokens + max_tokens ≤ context_window. Negative numbers raise `ValueError`.
6. Type hints on every public function. A docstring on `decode_step` that states which parts run on the new token only, and why the result equals the full pass.
7. The tests make no network call and need no API key.

## 6. Acceptance criteria

1. Given `data/block_toy.json`, the outputs of `run_with_cache` equal the outputs of `transformer_block(xs, params, causal=True)` for every token (tolerance 1e-12). The output for "sat" is [1.236, 0.829, -0.310, 2.958].
2. After the 3 tokens, `len(cache)` is 3, and cached key i equals layer norm 1 of token i times `w_k`.
3. Two calls of `run_with_cache` with the same input give the same outputs and caches of the same length.
4. `kv_cache_bytes(1, 32, 32, 128)` is 524,288. `kv_cache_bytes(4096, 32, 32, 128)` is 2,147,483,648. With 8 KV heads, the second value is 536,870,912.
5. `history_input_tokens(1000, [(200, 300)] * 10)` returns 10 values from 1,200 to 5,700, and their sum is 34,500.
6. `fits_context(4976, 1024, 6000)` is True and `fits_context(4977, 1024, 6000)` is False.
7. Given a system prompt of 1,000 tokens, 10 earlier pairs of 200 and 300 tokens, a new question of 200 tokens, max_tokens 1,024 and a window of 6,000, `trim_history` keeps the newest 7 pairs and the new question (15 messages, input 4,700 tokens). With a new question of 5,000 tokens, it raises `ContextBudgetError`.
8. `pytest` passes with the network off. `python -m assistant.kv_cache` prints a largest difference of 0.000 and the sizes of criterion 4.
