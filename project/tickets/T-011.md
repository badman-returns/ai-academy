## 2. Objective and real-world problem

Add a helpdesk triage command to the assistant. `python -m assistant.triage "message text"` prints a category and a priority for one employee message. Put the prompt logic in a new pure module, `assistant/triage.py`: the system prompt, the few-shot examples, the request builder and a strict parser. Prove it with tests that are named after the properties they check. Then write a labeled sample set of 20 fictional messages, and a script that measures the accuracy with 0, 1 and 3 examples.

**Real-world problem.** Teams change a prompt, try two messages by hand, and ship. Then a category that worked before breaks, and nobody sees it for a week. This ticket gives the assistant a triage prompt with one source in code, and a sample set that measures each prompt change.

## 5. Functional and technical requirements

**Functional**

1. `python -m assistant.triage "message text"` prints two lines, `category: ...` and `priority: ...`, and then the measurement line of T-001.
2. The categories are `IT`, `HR`, `facilities`, `finance` and `other`. The priorities are `low`, `medium` and `high`.
3. `--examples N` sets the number of examples: 0, 1 or 3. The default is 3. Another value gives an error before any API call.
4. When the reply does not parse, the command prints one clear line that says so, prints the measurement line, and exits with a code that is not 0. It never guesses a label.
5. `python scripts/triage_eval.py` runs every message of `samples/helpdesk.jsonl` with 0, 1 and 3 examples on `claude-haiku-5-5`. It prints one row for each run: examples, correct, accuracy, parse failures, input tokens and cost. Then it lists each wrong message of each run: id, expected labels and received labels.

**Technical**

1. `llm.py` stays the only module that calls the API.
2. `assistant/triage.py` contains `CATEGORIES`, `PRIORITIES`, `SYSTEM_PROMPT`, `load_examples(path)`, `build_request(message, examples)`, `parse_triage(text)` and `accuracy(expected, got)`. These functions are pure: no API calls, no printing, no global state that changes. Only the `main()` function at the end of the file calls `llm.py` and prints. The `__main__` block runs `main()`.
3. `build_request` returns the system prompt and the messages list. The system prompt holds the role, the task, the rules and the output format. Each example is one user turn (the message in `<message>` tags) and one assistant turn (the two label lines). The new message is the last user turn, in `<message>` tags.
4. The request never ends with an assistant turn: the current models return error 400 for a prefill. The request contains no `temperature`.
5. The system prompt is the same for every message. It contains no date, no message text and no user name.
6. The examples come from `samples/triage_examples.jsonl`. No example text is in `samples/helpdesk.jsonl`.
7. `parse_triage` reads the text blocks of the reply only (lesson 1.9). It accepts exactly one category line and one priority line with allowed values, with any case in the key and the value, and returns a `Label` dataclass with the values in their canonical form. For any other reply, it returns `None`.
8. The cost comes from `usage` with the T-001 price table.
9. The tests make no network call and need no API key. Reuse the fake client of T-001.

The system prompt must end with the format lines below, so that the parser and the prompt agree:

```
Reply with two lines and nothing else:
category: <one of IT, HR, facilities, finance, other>
priority: <one of low, medium, high>
```

## 6. Acceptance criteria

1. Given 3 examples, `build_request` returns 7 messages with the roles user, assistant, user, assistant, user, assistant, user. The last message contains the new message in `<message>` tags.
2. Given 0 examples, `build_request` returns 1 user message.
3. Given two different messages, the system prompt and all messages except the last are equal.
4. Given "category: IT" and "priority: high", `parse_triage` returns `Label("IT", "high")`. Given "Category: it" and "Priority: HIGH", it returns the same label.
5. Given "category: printer" and "priority: high", or "Sure! The category is IT.", `parse_triage` returns `None`.
6. Given the fake client with the reply "category: finance" and "priority: medium", the CLI prints these two lines and the measurement line, and exits with code 0.
7. Given the fake client with an unparsable reply, the CLI prints one error line with no stack trace and exits with a code that is not 0.
8. Given 20 expected labels and 13 correct replies, `accuracy` returns 0.65. A reply of `None` counts as wrong.
9. With a real key, `scripts/triage_eval.py` prints three rows (0, 1 and 3 examples). The handoff records the table and the list of wrong messages.
10. `pytest` passes with the network off. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the eval. The eval prints its total cost and the input tokens of each run, so you can see what the examples add. Run it one time, then read the results.
- **Reliability:** the parser accepts only the allowed values. A reply that does not parse is an error that the eval counts, never a guessed label.
- **Latency:** the reply is two short lines. Record the total time of each call in the eval, and report the median for each run.
- **Security:** the key comes only from the environment. The sample messages are fictional. The message text is data in `<message>` tags. Tags reduce the risk that a message changes the task, but they do not remove it, so the strict parser limits what a reply can do.
