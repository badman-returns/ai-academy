## 2. Objective and real-world problem

Add a `--mode` option to the triage command of T-011, with two new modes. `python -m assistant.triage --mode direct "message text"` asks for the two label lines in `<answer>` tags. `--mode reason` also asks the model to reason in `<reasoning>` tags before the answer. The code takes out only the answer and never shows the reasoning to the employee. A response without exactly one answer section is an error. Put the logic in a new pure module, `assistant/reasoning.py`, and prove it with tests that are named after the properties they check. Then run the sample set of T-011 in both modes, and compare the accuracy, the output tokens and the cost.

**Real-world problem.** Teams add "think step by step" to a prompt to fix a few hard requests. Then the reasoning leaks into the replies that users see, the parser breaks when the tags are missing, the bill goes up on every request, and on a large model the prompt is declined and still billed. This ticket adds the mode with the checks that prevent these failures, and a measurement that shows if the mode is worth its cost.

## 5. Functional and technical requirements

**Functional**

1. `--mode` takes `labels`, `direct` or `reason`. The default is `labels`: the T-011 command with no change. `--mode direct` asks for the two label lines inside `<answer>` tags. `--mode reason` adds the instruction to reason inside `<reasoning>` tags first. In both new modes, the CLI prints only the two label lines, as T-011 does.
2. The CLI never prints the reasoning text or any other text outside the answer section.
3. When the response has no answer section, two or more answer sections, or an empty answer section, the CLI prints one clear line, for example `could not read the triage answer: expected 1 answer section, found 0`, and exits with a code that is not 0. It prints no stack trace.
4. When `stop_reason` is `refusal` or `max_tokens`, the CLI reports the status of T-009 `check_answer`, does not parse the text, and exits with a code that is not 0.
5. In the two new modes, the measurement line of T-001 gets two fields: `mode` (`direct` or `reason`) and `answer` (`ok`, `incomplete`, `no_answer`, `refusal` or `format_error`). Example: `mode=reason answer=ok`.
6. `python scripts/triage_eval.py --modes direct,reason` runs every message of `samples/helpdesk.jsonl` in each mode, with the 3 examples of T-011. It prints one table row per mode: correct answers, accuracy, format errors (answer-tag errors and `parse_triage` failures), mean input tokens, mean output tokens, median time, total cost and cost per correct answer. Then it lists each wrong message of each mode, as T-011 does. Without `--modes`, the script works as in T-011.

**Technical**

1. `llm.py` stays the only module that calls the API.
2. `assistant/reasoning.py` contains pure code only: `MODES`, `ANSWER_INSTRUCTION`, `REASON_INSTRUCTION`, `AnswerFormatError`, `extract_answer`, `system_prompt` and `request_options`. No API calls, no printing, no global state.
3. `extract_answer(text)` uses one regular expression, `<answer>(.*?)</answer>` with `re.DOTALL`. It returns the trimmed text of exactly one non-empty section. In all other cases, it raises `AnswerFormatError` with a message that gives the number of sections found.
4. `system_prompt(rules, label_format, reason)` joins the rules of the T-011 prompt, `ANSWER_INSTRUCTION` followed by the T-011 format lines, and, in the reason mode, `REASON_INSTRUCTION`. In `triage.py`, split `SYSTEM_PROMPT` into `RULES` and `LABEL_FORMAT` (the two format lines), and build `SYSTEM_PROMPT` from them with the same text as before. Then the prompt has one source, and the T-011 tests do not change.
5. `build_request` of T-011 gets an optional parameter `answer_tags: bool = False`. When it is true, each example assistant turn has its two label lines inside `<answer>` tags. The examples have no reasoning section.
6. `request_options(mode, model)` returns the extra request arguments. Both modes use `claude-haiku-5-5` and send `thinking={"type": "disabled"}`. For any other model, it raises `ValueError` before any API call. The message says why: Opus 5.5 and Sonnet 5.5 reject `"disabled"` with error 400, and they can decline a prompt that asks for a reasoning section (`reasoning_extraction`).
7. The triage sends no effort above `high`, because Haiku 5.5 accepts `"disabled"` only at effort low, medium or high.
8. The CLI calls `check_answer` first, then `extract_answer` on the joined text, then `parse_triage` of T-011 on the answer. When `parse_triage` returns `None`, the CLI prints the T-011 error line, and the measurement line has `answer=format_error`.
9. Never prefill an assistant turn with `<answer>`: the current models return error 400. Never send `temperature`, `top_p` or `top_k`.
10. The cost comes from `usage.input_tokens` and `usage.output_tokens` with the T-001 price table. The cost per correct answer uses `cost_per_correct` of T-009.
11. The raw response text never goes to a log, because it contains the employee message and the reasoning. Log the error type and the request id.
12. The tests make no network call and need no API key. Reuse the fake client of T-001.

## 6. Acceptance criteria

1. Given mode `reason` and the fake client, the request arguments contain `model="claude-haiku-5-5"`, `thinking={"type": "disabled"}`, and a system prompt that contains `REASON_INSTRUCTION`. Given mode `direct`, the system prompt does not contain `REASON_INSTRUCTION`. In both modes, the system prompt contains `ANSWER_INSTRUCTION` and the T-011 format lines, and each example assistant turn has its two label lines inside answer tags.
2. Given `--mode reason` with `--model claude-opus-5-5`, the CLI prints the error of `request_options`, exits with a code that is not 0, and the fake client records 0 calls.
3. Given the response text `<reasoning>Access groups belong to IT.</reasoning>` followed by an answer section with `category: IT` and `priority: high`, the CLI output contains `category: IT` and does not contain "Access groups belong to IT" or `<reasoning>`.
4. Given the text `category: IT` with no tags, `extract_answer` raises `AnswerFormatError` with "found 0", the CLI exits with a code that is not 0, the measurement line has `answer=format_error`, and there is no stack trace.
5. Given reasoning that contains a draft `<answer>facilities</answer>`, followed by a final answer section, `extract_answer` raises `AnswerFormatError` with "found 2".
6. Given `stop_reason="refusal"` and empty content, the status is `refusal`, and `extract_answer` is not called.
7. Given usage of 1,180 input and 48 output tokens at the Haiku 5.5 prices of the T-001 table ($0.10 and $0.50 per million), the cost is 0.000142. Given 1,240 and 150, it is 0.000199 (tolerance 1e-12 for both). These are the examples of the lesson.
8. Given 20 runs that cost $0.00398 in total with 18 correct answers, `cost_per_correct` returns 0.000221 (tolerance 1e-6).
9. With a real key, `scripts/triage_eval.py --modes direct,reason` runs the sample set in both modes. The handoff records the table.
10. `pytest` passes with the network off. The tests of T-001, T-009 and T-011 pass without a change. The key value appears in no file and in no log line.

## 10. Security, reliability, performance and cost

- **Cost:** use `claude-haiku-5-5` for all manual tests and for the eval. The eval prints its total cost. Run it one time, then read the results. The unit tests make no paid calls.
- **Reliability:** never show a response with a format error, a refusal or a `max_tokens` stop as a triage result. Every such case is visible in the measurement line.
- **Latency:** record the total time of each call in the eval. The reasoning comes before the answer, so the reason-first mode is slower. Report the median per mode, and say that 20 messages are too few for a p95.
- **Privacy:** the reasoning repeats details of the employee message. The CLI never prints it, and no log contains the raw text.
